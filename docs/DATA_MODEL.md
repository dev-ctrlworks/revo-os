# Data Model

**Document type:** Database and data architecture specification
**Product:** RevoOS
**Status:** Proposed
**Primary database:** Supabase PostgreSQL
**File storage:** Supabase Storage
**Purpose:** Define the canonical data structures, relationships, constraints, and access rules for RevoOS.
* * *

## 1\. Data Model Principles
1. **PostgreSQL is the source of truth.** All canonical memory metadata and relationships are stored in the database.
2. **Preserve original content.** Never replace a user's original file, URL, or note with an AI-generated summary.
3. **Support multiple memory types.** Links, notes, images, documents, and screenshots share a common memory model.
4. **Keep organization flexible.** Tags, collections, and relationships are distinct features.
5. **Private by default.** Every personal memory belongs to one user and is inaccessible to other users unless sharing is explicitly implemented.
6. **Make AI outputs traceable.** Summaries, extracted text, and embeddings must be associated with the source memory and version they represent.
7. **Avoid unnecessary duplication.** Store reusable metadata once and use join tables for many-to-many relationships.
8. **Support incremental development.** The initial schema should work for personal use while allowing future graph, collaboration, and mobile features.
9. **Use stable identifiers.** Prefer UUIDs for database entities rather than filenames, URLs, titles, or display labels.
10. **Model real product behavior.** Do not add speculative entities or complex abstractions without a concrete use case.
## 2\. Entity Relationship Overview
The core personal-memory model consists of:
*   `profiles`
*   `memories`
*   `memory_files`
*   `tags`
*   `memory_tags`
*   `collections`
*   `collection_memories`
*   `memory_relationships`
Additional processing and AI tables can be introduced when needed.

```gherkin
erDiagram
    PROFILES ||--o{ MEMORIES : owns
    MEMORIES ||--o{ MEMORY_FILES : contains
    PROFILES ||--o{ TAGS : creates
    MEMORIES ||--o{ MEMORY_TAGS : assigned
    TAGS ||--o{ MEMORY_TAGS : labels
    PROFILES ||--o{ COLLECTIONS : owns
    COLLECTIONS ||--o{ COLLECTION_MEMORIES : contains
    MEMORIES ||--o{ COLLECTION_MEMORIES : included
    MEMORIES ||--o{ MEMORY_RELATIONSHIPS : source
    MEMORIES ||--o{ MEMORY_RELATIONSHIPS : target
```

All personal relationships must respect user ownership. A valid foreign key alone does not prove that the linked records belong to the same user.
## 3\. Identifier and Naming Conventions
*   Use UUID primary keys, generated by PostgreSQL.
*   Use `snake_case` for database table and column names.
*   Use `timestamptz` for timestamps.
*   Use UTC-compatible timestamps and convert to the user's locale in the UI.
*   Use explicit foreign keys and appropriate delete behavior.
*   Use constrained text values or PostgreSQL enums for stable status/type fields.
*   Prefer check constraints when they are easier to evolve than database enums.
*   Use `jsonb` only for flexible metadata, not for core relationships.
*   Keep display names separate from internal identifiers.
Suggested common columns for user-owned entities:

| Column | Type | Purpose |
| ---| ---| --- |
| `id` | `uuid` | Primary key |
| `user_id` | `uuid` | Owner |
| `created_at` | `timestamptz` | Creation time |
| `updated_at` | `timestamptz` | Last update time |

Use these common fields where applicable rather than forcing identical columns onto every table.
## 4\. Profiles
### Table: `profiles`
Stores application-specific user preferences. Supabase Auth remains responsible for authentication identity and credentials.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key; references `auth.users.id` |
| `display_name` | `text` | No | User's preferred display name |
| `avatar_path` | `text` | No | Optional private or controlled avatar storage key |
| `preferences` | `jsonb` | Yes | UI and product preferences; default `{}` |
| `created_at` | `timestamptz` | Yes | Creation time |
| `updated_at` | `timestamptz` | Yes | Last update time |

### Rules
*   Create the profile when an account is provisioned, using a trusted server-side process or carefully secured database trigger.
*   Do not duplicate passwords, authentication tokens, or other authentication secrets.
*   Validate the allowed shape of `preferences` at the application boundary.
*   Avoid storing sensitive personal information that is not required by the product.
## 5\. Memories
### Table: `memories`
The central entity in RevoOS. Every saved item has one memory record regardless of whether its source is a webpage, note, screenshot, image, or document.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key |
| `user_id` | `uuid` | Yes | Owner; references `auth.users.id` |
| `type` | `text` | Yes | `link`, `note`, `image`, `document`, or `screenshot` |
| `title` | `text` | Yes | Display title |
| `description` | `text` | No | User-written description or contextual note |
| `source_url` | `text` | No | Original webpage URL where applicable |
| `source_domain` | `text` | No | Normalized hostname for filtering and display |
| `content_text` | `text` | No | Original text content for text-based memories |
| `extracted_text` | `text` | No | Text extracted from a document or image |
| `ai_summary` | `text` | No | Generated summary, kept separate from original content |
| `metadata` | `jsonb` | Yes | Optional type-specific metadata; default `{}` |
| `processing_status` | `text` | Yes | `pending`, `processing`, `ready`, or `failed` |
| `processing_error_code` | `text` | No | Safe, machine-readable processing error code |
| `captured_at` | `timestamptz` | No | Original capture time when available |
| `created_at` | `timestamptz` | Yes | Record creation time |
| `updated_at` | `timestamptz` | Yes | Last metadata/content update time |

### Memory type behavior
**Link**
*   Store the original URL.
*   Store the title and supported page metadata.
*   Store extracted page text only when available and permitted.
**Note**
*   Store the original note in `content_text`.
*   Preserve user-entered content exactly unless the user edits it.
**Image**
*   Store the file reference in `memory_files`.
*   Keep OCR text in `extracted_text` when available.
**Document**
*   Store the original document in `memory_files`.
*   Keep extracted text separate from the original document.
**Screenshot**
*   Store the image file in `memory_files`.
*   Preserve the source URL or capture metadata when available.
### Rules
*   `user_id` is mandatory for personal memories.
*   `title` must not be empty after trimming.
*   Validate `type` against the supported values.
*   `source_url` is optional because not every memory comes from a webpage.
*   Do not put file bytes, large extracted documents, or embeddings into `metadata`.
*   `ai_summary` is disposable derived data; it must never replace the original.
*   A failed extraction must not make the original memory unavailable.
*   Track source-content changes so summaries, embeddings, and extracted text can be refreshed appropriately.
### Context preservation
RevoOS should support why a memory was saved, not merely where it came from.
Use `description` for an optional user-authored note about relevance or intent. A future structured context feature may model projects or topics separately. Do not infer a user's original reason for saving something unless they provided it or the system clearly labels it as a generated suggestion.
## 6\. Memory Files
### Table: `memory_files`
Represents uploaded or captured files associated with a memory. A memory may have multiple files, such as an original upload and a generated thumbnail.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key |
| `memory_id` | `uuid` | Yes | Parent memory |
| `user_id` | `uuid` | Yes | Owner; supports ownership checks |
| `storage_path` | `text` | Yes | Private storage object key |
| `original_filename` | `text` | Yes | Filename supplied by the user or source |
| `mime_type` | `text` | Yes | Validated content type |
| `file_size_bytes` | `bigint` | Yes | File size in bytes |
| `role` | `text` | Yes | For example, `original`, `thumbnail`, or `derived` |
| `checksum` | `text` | No | Optional content checksum |
| `created_at` | `timestamptz` | Yes | Creation time |

### Rules
*   Store the binary object in Supabase Storage, not in the table.
*   Require a unique storage path.
*   Reject invalid or negative file sizes.
*   Enforce upload limits and supported formats at the application boundary.
*   Ensure the parent memory and file record belong to the same user.
*   Do not trust the file extension or client-provided MIME type by itself.
*   Treat filenames as untrusted input.
*   Use private buckets and authorized, short-lived download URLs.
If multiple files are allowed for one memory, choose a clear default-file rule or ordering strategy rather than assuming every memory has exactly one file.
## 7\. Tags
### Table: `tags`
Tags are user-owned labels for categorizing and filtering memories.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key |
| `user_id` | `uuid` | Yes | Owner |
| `name` | `text` | Yes | Display name |
| `normalized_name` | `text` | Yes | Normalized form for duplicate detection |
| `created_at` | `timestamptz` | Yes | Creation time |

### Table: `memory_tags`
Connects memories to tags using a many-to-many relationship.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `memory_id` | `uuid` | Yes | Memory reference |
| `tag_id` | `uuid` | Yes | Tag reference |
| `created_at` | `timestamptz` | Yes | Assignment time |

### Rules
*   A tag belongs to one user.
*   A memory can have multiple tags.
*   A tag can label multiple memories.
*   Prevent duplicate normalized tag names per user.
*   Prevent duplicate memory/tag assignments.
*   Ensure both the tag and memory belong to the same user.
*   Tag management happens contextually in the Library, memory details, and collection workflows.
*   **Do not add Tags as a primary navigation destination.**
Normalize tag names consistently in application logic, including trimming whitespace and applying a defined case-normalization rule.
## 8\. Collections
### Table: `collections`
Collections are user-created groups of memories.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key |
| `user_id` | `uuid` | Yes | Owner |
| `name` | `text` | Yes | Collection title |
| `description` | `text` | No | Optional purpose or context |
| `cover_memory_id` | `uuid` | No | Optional memory used as the cover |
| `created_at` | `timestamptz` | Yes | Creation time |
| `updated_at` | `timestamptz` | Yes | Last update time |

### Table: `collection_memories`
Joins collections and memories.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `collection_id` | `uuid` | Yes | Collection reference |
| `memory_id` | `uuid` | Yes | Memory reference |
| `added_at` | `timestamptz` | Yes | Time added |

### Rules
*   A collection belongs to one user in the initial release.
*   A collection can contain many memories.
*   A memory can belong to multiple collections.
*   Prevent duplicate collection/memory assignments.
*   Ensure the collection and memory belong to the same user.
*   A collection cover must refer to an authorized memory owned by the same user.
*   Deleting a collection must not delete its memories.
*   Removing a memory from a collection must not delete the memory itself.
Collections are for deliberate grouping; tags are lightweight labels. Do not merge these concepts into one table.
## 9\. Memory Relationships
### Table: `memory_relationships`
Stores explicit relationships between two memories. This table provides the initial foundation for backlinks and the knowledge graph.

| Column | Type | Required | Description |
| ---| ---| ---| --- |
| `id` | `uuid` | Yes | Primary key |
| `user_id` | `uuid` | Yes | Owner |
| `source_memory_id` | `uuid` | Yes | Origin memory |
| `target_memory_id` | `uuid` | Yes | Related memory |
| `relationship_type` | `text` | Yes | Type of connection |
| `created_by` | `text` | Yes | `user` or `ai` |
| `created_at` | `timestamptz` | Yes | Creation time |

### Initial relationship types
*   `related_to`
*   `references`
*   `derived_from`
*   `contradicts`
Treat these as an initial vocabulary, not a requirement to implement every type immediately.
### Rules
*   Both memories must belong to the same owner in the personal-memory model.
*   Prevent self-links unless a specific future use case requires them.
*   Prevent duplicate directed relationships of the same type.
*   Define whether relationships are directional or symmetric.
*   For a symmetric type such as `related_to`, use a consistent ordering strategy or enforce a canonical pair so that A–B and B–A do not become duplicates.
*   Backlinks should be computed from relationship records rather than stored redundantly.
*   AI-suggested relationships should be distinguishable from user-confirmed relationships.
Do not create a graph database for the MVP. PostgreSQL is sufficient for the initial relationship model.
## 10\. Content Processing and AI Artifacts
Content extraction and AI processing need to be reliable, observable, and safe to retry.
### Processing status
The `memories.processing_status` field represents the overall state for the initial implementation.
Use explicit, documented transitions:
*   `pending` → `processing`
*   `processing` → `ready`
*   `processing` → `failed`
*   `failed` → `pending` when a retry is scheduled
Avoid marking a memory ready while required processing is incomplete. If different processing tasks need independent states, introduce task-level records rather than overloading a single field.
### Optional future table: `memory_processing_jobs`
Introduce when background jobs and retries need durable tracking.
Possible fields:
*   `id`
*   `memory_id`
*   `user_id`
*   `job_type`
*   `status`
*   `attempt_count`
*   `last_error_code`
*   `started_at`
*   `completed_at`
*   `created_at`
*   `updated_at`
Use a constrained job type, idempotent processing where possible, and retry limits. Do not store sensitive error payloads unnecessarily.
### Optional future table: `memory_embeddings`
Introduce when semantic search is implemented.
Possible fields:
*   `id`
*   `memory_id`
*   `user_id`
*   `source_version`
*   `embedding_model`
*   `embedding`
*   `created_at`
Use a vector dimension that matches the selected embedding model and the pgvector schema. Store one or more embeddings only if the retrieval strategy requires them.
Embeddings must be regenerated when the source content or relevant model configuration changes. Search must apply ownership restrictions before exposing matches.
### AI summary lifecycle
A summary should be refreshed when its underlying content changes, not every time a memory is opened.
For more rigorous version tracking, add fields such as:
*   `summary_source_version`
*   `summary_model`
*   `summary_generated_at`
Avoid creating a separate summary-history table unless users need version history or auditability.
## 11\. Search Architecture
### Initial keyword search
Use PostgreSQL full-text search and indexes to search available content.
Searchable fields may include:
*   Title.
*   User-authored description.
*   Note content.
*   Extracted document text.
*   AI summary, if available.
*   Source metadata when useful.
Choose language configuration and ranking behavior based on the product's language requirements.
### Search indexing
Use a generated `tsvector` column or a maintained search document, depending on the final schema. Index it with GIN where appropriate.
Keep the search document synchronized with changes to the source fields through a deliberate database or application strategy. Do not let the search index become the canonical source of content.
### Future semantic search
Use pgvector and a hybrid retrieval approach when semantic recall is introduced. Embeddings are derived data, not replacements for searchable original content.
Every search operation must scope results to the authorized user. AI retrieval must follow the same rule.
## 12\. Indexing Strategy
Create indexes for actual access patterns rather than indexing every column.
Recommended initial indexes:
*   `memories(user_id, created_at DESC)`
*   `memories(user_id, type)`
*   `memories(user_id, processing_status)`
*   Full-text GIN index for the memory search document
*   Unique `tags(user_id, normalized_name)`
*   Unique `memory_tags(memory_id, tag_id)`
*   Unique `collection_memories(collection_id, memory_id)`
*   Index `collection_memories(memory_id)`
*   Index `memory_files(memory_id)`
*   Unique `memory_files(storage_path)`
*   Index `memory_relationships(source_memory_id)`
*   Index `memory_relationships(target_memory_id)`
Add indexes on other foreign keys as query patterns require. Consider owner-scoped composite indexes where they improve common access paths.
For relationship and join tables, ensure indexes support both authorization checks and common reverse lookups.
## 13\. Data Integrity and Deletion
### Foreign keys
Use explicit foreign keys for all canonical relationships.
Recommended behavior:
*   Deleting a memory should remove its tag assignments, collection memberships, and relationship records.
*   Deleting a collection should remove collection membership records, not the memories themselves.
*   Deleting a tag should remove its assignments, not the memories themselves.
*   Deleting a user should trigger a defined account-deletion workflow that removes or anonymizes owned database records and cleans up storage objects.
### File cleanup
Database deletion and object-storage deletion may not be one atomic transaction.
Implement a reliable cleanup workflow:
1. Authorize the deletion.
2. Delete or mark the relevant database records according to the selected policy.
3. Schedule or perform storage-object cleanup.
4. Retry failed cleanup operations.
5. Avoid leaving inaccessible private objects indefinitely.
Do not assume a database cascade automatically deletes a file from object storage.
### Hard delete versus soft delete
For the initial release, use hard deletion where it satisfies the product's requirements and can be performed reliably.
Introduce a `deleted_at` field only if the product needs trash, recovery, retention periods, or delayed deletion. If soft deletion is added, ensure every read, search, relationship, and storage-access path respects it.
## 14\. Security and Row Level Security
Enable RLS on every table that contains user-owned data or can expose private information.
At minimum, define policies for:
*   Profiles.
*   Memories.
*   Memory files.
*   Tags and memory tags.
*   Collections and collection memberships.
*   Memory relationships.
*   Processing jobs.
*   Embeddings.
### Ownership invariants
For the initial personal model:
*   `memories.user_id` must identify the owner.
*   Related files must have the same owner as their parent memory.
*   Tags and memories linked through `memory_tags` must have the same owner.
*   Collections and memories linked through `collection_memories` must have the same owner.
*   Both ends of a personal memory relationship must belong to the relationship owner.
*   Processing jobs and embeddings must be restricted to the owner of their parent memory.
Enforce these invariants with a combination of foreign keys, carefully designed constraints, RLS, and server-side authorization. Where cross-row constraints are required, choose a robust database enforcement strategy rather than relying only on frontend checks.
Storage policies must also verify the authenticated user's right to access each object. A predictable storage path is not a substitute for authorization.
See `docs/SECURITY_AND_PRIVACY.md` for the complete security policy.
## 15\. Future Shared Workspaces
Collaboration is planned for a later phase and should not complicate the personal MVP unnecessarily.
When sharing is implemented, consider adding:
*   `workspaces`
*   `workspace_members`
*   `workspace_memories` or explicit memory ownership/placement rules
*   Role and permission definitions
*   Sharing audit records, if required
Before implementation, decide whether shared memories:
1. Belong to a workspace independently of any personal owner, or
2. Remain personally owned and are shared through explicit grants.
Do not mix these ownership models without a clear rule. Define how moving, copying, sharing, and deleting memories work.
All collaboration features must preserve existing private-memory boundaries.
## 16\. Data Model Rules for OpenCode
1. Read this document before creating or changing database schema.
2. Inspect existing migrations and types before adding new tables.
3. Keep all schema changes in version-controlled migrations.
4. Preserve original content separately from derived content.
5. Use UUIDs and explicit foreign keys.
6. Enforce ownership across all linked entities.
7. Enable RLS on private tables and write tests for cross-user access.
8. Do not add a primary Tags navigation item.
9. Do not create speculative tables solely for features that are not yet being built.
10. Do not store file bytes, secrets, or large unstructured documents in `metadata`.
11. Do not treat AI summaries, embeddings, or extracted text as canonical originals.
12. Keep search results and AI retrieval scoped to the authenticated user's permissions.
13. Do not claim security is complete until policies and access tests have been verified.
14. Update this document when the actual schema changes.
## 17\. MVP Schema Scope
Implement these entities first:
*   `profiles`
*   `memories`
*   `memory_files`
*   `tags`
*   `memory_tags`
*   `collections`
*   `collection_memories`
Add `memory_relationships` when explicit linking is part of the active release scope. The table can be introduced early if the initial app already includes basic relationships, but graph visualization is not required for the first capture release.
Defer processing-job tables and embeddings until the actual processing and semantic-search implementation requires them.
### MVP acceptance criteria
*   Users can create and manage their own memories.
*   Memory records support the five initial item types.
*   Original uploaded files are stored privately.
*   Tags and collections work without duplicating memory records.
*   Deleting a memory cleans up its database relationships.
*   Ownership is enforced for all reads and writes.
*   Search returns only authorized memories.
*   Derived AI content can be regenerated without destroying originals.
*   Database migrations reproduce the schema reliably in a fresh environment.
* * *

## Final Decision
Use a shared `memories` table for all saved content, separate file metadata from binary storage, and model tags, collections, and memory relationships through explicit join tables.
Keep PostgreSQL as the source of truth and enforce personal ownership throughout the schema. Add embeddings, durable processing jobs, and workspace entities only when their corresponding product phases are implemented.
