# Database

Revo OS has two data stores:

1. **Supabase (Postgres)** — the only server-side persistent store, holding the
   public `waitlist` and `feedback` tables.
2. **Browser `localStorage`** — where every captured memory actually lives
   (the "local-first" model). There is no server-side memory database.

There are no migration files in the repository. The Supabase schema is
provisioned manually; the canonical SQL is reproduced here (and in the
`README.md`).

## Supabase setup

Create a project, then run:

```sql
create table if not exists waitlist (
  id uuid primary key default gen_random_uuid(),
  email text unique not null,
  created_at timestamptz default now()
);
alter table waitlist enable row level security;
create policy "public insert" on waitlist for insert with check (true);

create table if not exists feedback (
  id uuid primary key default gen_random_uuid(),
  message text not null,
  email text,
  page text,
  created_at timestamptz default now()
);
alter table feedback enable row level security;
create policy "public insert" on feedback for insert with check (true);
```

## Tables

### `waitlist`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK, `gen_random_uuid()`. |
| `email` | `text` | `unique not null`. Uniqueness enforced by a unique index; duplicate inserts raise Postgres error `23505`. |
| `created_at` | `timestamptz` | Defaults to `now()`. |

- **Writes:** `POST /api/waitlist` inserts `{ email }`. A `23505` unique
  violation is treated as success (idempotent signup).
- **Reads:** `GET /api/counts` runs a head/exact-count query (`select("id",
  { count: "exact", head: true })`) and returns `{ waitlist: count }`, cached
  `public, s-maxage=60, stale-while-revalidate=300`.
- **Privacy:** `POST /api/privacy` exports `email, created_at` by case-
  insensitive email match, or deletes matching rows.

### `feedback`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK, `gen_random_uuid()`. |
| `message` | `text` | Required, max 2000 chars (validated in the route). |
| `email` | `text` | Optional, max 320 chars, regex-validated. |
| `page` | `text` | Optional, max 200 chars, recorded from the client. |
| `created_at` | `timestamptz` | Defaults to `now()`. |

- **Writes:** `POST /api/feedback` inserts `{ message, email, page }`.
- **Privacy:** exported as `message, page, created_at` (email is not echoed
  back, since it is the query key); deleted by email match.

### Row Level Security

RLS is enabled on both tables with a permissive `public insert` policy. The
application does **not** rely on RLS: it connects with the **service-role key**
(`src/lib/supabase.ts`), which bypasses RLS. RLS here is defense-in-depth so
that if the anon key were ever used directly, anonymous clients could still
only insert — never read or delete.

> Why the service role: the privacy export/delete endpoints need to read and
> delete by email, and `/api/counts` needs a count, neither of which the
> insert-only policy allows.

## Client: `localStorage`

All memory data is namespaced under `revoos.*`. The store logic is in
`src/lib/memory-store.ts`.

| Key | Contents | Purpose |
| --- | --- | --- |
| `revoos.captured.memories.v1` | `Memory[]` | Memories the user captured. |
| `revoos.memory-edits.v1` | `Record<id, Partial<Memory>>` | Edits applied on top of base or captured memories. |
| `revoos.collection-meta.v1` | `Record<name, Partial<CollectionMeta>>` | Collection emoji/description/color overrides and created collections. |
| `revoos.deleted-memories.v1` | `string[]` | Tombstones for deleted memories (needed to hide base demo data). |
| `revoos.asked-count.v1` | `number` | Count of AI questions asked. |
| `revoos.dashboard.v1` | JSON (zustand persist) | Persisted dashboard `viewMode` and `sidebarCollapsed`. |
| `revo-consent-v1` | `"granted" \| "denied"` | Analytics consent. |

### The `Memory` record

Defined in `src/lib/types.ts`:

```ts
interface Memory {
  id: string;              // "m1" for base data; "cap-<ts>-<rand>" for captures
  type: MemoryType;        // screenshot | note | document | link | image |
                           // discussion | email | archive
  title: string;
  content: string;
  createdAt: string;       // ISO 8601
  source: string;          // "note", "clipboard", a URL, or "Upload · filename"
  domain?: string;
  tags: string[];
  favorite: boolean;
  collection: string;      // defaults to "New captures"
  highlight?: string;
  summary?: string;        // generated by summarize.ts
  description?: string;    // generated by summarize.ts
  keyPoints?: string[];
  previewUrl?: string;
}
```

### Composition rules

`getAllMemories()` returns the effective list:

1. Concatenate captured memories (newest first) followed by base memories.
2. Drop any whose id is in the deleted tombstone set.
3. Apply `memory-edits.v1` patches (`{ ...memory, ...edits[id] }`).

Renames and moves are implemented as edit patches; deleting a base memory
records a tombstone. `clearCapturedMemories()` removes captured entries and
their `cap-` edits, while leaving base-data tombstones intact.

### Capacity and failure handling

- `STORAGE_LIMIT_BYTES = 5_000_000` (~5 MB), reported by
  `getStorageUsageBytes()` / `getStorageLimitBytes()` and shown in Settings.
- Any `setItem`/`removeItem` failure sets `storageWarning` to
  `STORAGE_FULL_MESSAGE`, surfaced by `StorageWarningBanner` in the capture UI.
- All reads are defensive: `safeParse*` helpers swallow malformed JSON and
  return `[]`/`{}`.

### SSR and hydration

`getSnapshot()` returns the cached client snapshot, `getServerSnapshot()`
returns only base memories, and `syncFromStorage()` (called in an effect)
flips a `hydratedFromStorage` flag and triggers a re-read. This keeps the
server-rendered HTML and the first client render identical, then upgrades to
the full local set after hydration.
